How to use these labs

  • Everything you do today happens on one small project, pulselab, written the way research code often is: it works, it is not documented, it has few tests, and it hides a few traps.
  • The labs follow the training modules. Each lab has goals, numbered steps, a suggested mode, checks and deliverables. Tick each step when it is done (your ticks are saved in this browser).
  • Tool-agnostic: every step names a mode (CHAT, PLAN, EDIT, AGENT, REVIEW), not a product. Use the closest equivalent in your company's approved tool. If your tool lacks a mode, emulate it (table below) and note it in your journal.
  • Prompts are yours to write. The dashed boxes give a structure with blanks: the six blocks (goal, context, constraints, examples, format, verification). The point is to practise writing them.
  • Time boxes are indicative. CORE labs are the priority; a STRETCH lab is done if time allows.
Safety rules, all day: no secrets, no confidential data and no unpublished results in any prompt (the data of this project is synthetic). Commit before any AI action that can edit files, and read the diff afterwards.

The five modes: a tool-agnostic vocabulary

  • Fill the last column with the name your tool uses. If a mode does not exist, use the emulation below.
ModeMeaningIn MY tool it is called…
CHATQuestion / answer, no file changes
PLANPlan only, nothing is edited
EDITTargeted edits you review one by one
AGENTAutonomous: reads, edits, runs commands
REVIEWRead-only review of a diff or file
  • No PLAN mode? Ask in CHAT: “Do not write code. Give me a numbered plan: files to change, order, risks.”
  • No AGENT mode? Work in CHAT/EDIT, apply the changes yourself and run the commands yourself. Note the extra effort in your journal.
  • No REVIEW mode? Paste the diff in CHAT and ask for comments only, no rewrite.

Golden rules for every lab

  • Branch and commit. One branch per lab, small commits, so any AI change is reviewable and reversible.
  • Verify. Run the tests, run the code, open the files the assistant cites. A confident answer is not evidence.
  • Small steps. One change per prompt. Restart a session that has drifted.
  • You own what you commit. Read every line of every diff you accept.
  • Keep your AI journal (bottom of the page): prompt → what happened → how you verified → verdict → lesson.

TP 1.2 · Prompting lab: from a weak prompt to a reusable template

Learning goals
  • See the effect of the six blocks (goal, context, constraints, examples, format, verification) on a numerical task.
  • Use assumptions + questions and exact-error feedback to iterate.
  • Leave with a reusable prompt template.

Task: add a function pulse_widths_fwhm(x, fs, idx) in a new file pulselab/pulses.py. It returns the full width at half maximum (in seconds) of each pulse of a signal, given the sample indices idx of the pulse maxima (as returned by find_pulses). The baseline of x is around 0 V. If the half-maximum level is not crossed before the end of the record, the width of that pulse is NaN.

Work on a branch: git switch -c tp1-2-prompting. This lab is separate from the next ones: you will not keep the code in the main project, only your prompt template.
1.2.1Copy the acceptance tests (they define 'done')HUMAN3 min
  • Create tests/test_pulse_width.py with the tests below. They fail now (the module does not exist). They contain an analytical check: a Gaussian of standard deviation σ has FWHM = 2√(2 ln 2)·σ.
tests/test_pulse_width.py
import numpy as np
import pytest

from pulselab.pulses import pulse_widths_fwhm

FS = 1000.0
SIGMA = 0.01                       # s   ->   FWHM = 2 * sqrt(2 ln 2) * sigma = 0.023548 s


def _gaussian_pulse(center_s, amp=1.0, n=1000):
    t = np.arange(n) / FS
    return amp * np.exp(-0.5 * ((t - center_s) / SIGMA) ** 2)


def test_gaussian_fwhm_is_recovered():
    w = pulse_widths_fwhm(_gaussian_pulse(0.5), FS, [500])
    assert w[0] == pytest.approx(2 * np.sqrt(2 * np.log(2)) * SIGMA, rel=0.03)


def test_amplitude_does_not_change_the_width():
    a = pulse_widths_fwhm(_gaussian_pulse(0.5, 1.0), FS, [500])[0]
    b = pulse_widths_fwhm(_gaussian_pulse(0.5, 5.0), FS, [500])[0]
    assert a == pytest.approx(b, rel=1e-6)


def test_two_pulses_give_two_widths():
    x = _gaussian_pulse(0.3) + _gaussian_pulse(0.7)
    assert pulse_widths_fwhm(x, FS, [300, 700]).shape == (2,)


def test_pulse_cut_by_the_end_of_the_record_gives_nan():
    assert np.isnan(pulse_widths_fwhm(_gaussian_pulse(0.999), FS, [999])[0])


def test_no_pulse_gives_an_empty_array():
    assert pulse_widths_fwhm(np.zeros(100), FS, []).size == 0
Check before you move on
  • python -m pytest -q tests/test_pulse_width.py fails with an import error.

TP 1.4 · Implement a multi-file feature: band power

Learning goals

Feature request. Researchers want to know how much signal power lies in a frequency band. Add a --band FMIN FMAX option to the analysis script that adds a band_power_V2 column to the summary.

1.4.1Read the specification and write your acceptance checklistHUMAN4 min
#Acceptance criterion
AC1spectrum.band_power(x, fs, fmin, fmax, nperseg=1024) returns the power (V²) in [fmin, fmax] Hz as a float: Welch PSD (scipy.signal.welch) integrated over the band, bounds inclusive.
AC2A sine of amplitude A at f0 inside the band gives ≈ A²/2 (±5 %); outside the band ≈ 0; a DC offset does not count.
AC3fmin >= fmax raises ValueError.
AC4CLI option --band FMIN FMAX (two floats, optional). When given, the CSV gets the column band_power_V2 as the last column. When absent, the CSV is identical to before.
AC5README documents the option; tests added; all existing tests still pass.

TP 1.5 · Fix a complex bug: reproduce, hypothesize, verify, fix

Learning goals
  • Apply the debugging method: evidence → ranked hypotheses → experiment → root-cause fix → regression test.
  • Notice when a plausible fix hides the symptom instead of removing the cause.

A colleague sends you this report:

bug report
Subject: summary.csv looks wrong

Hi, two things I cannot explain in the summary table:
1) The offset_V column is ~0.0000 for ALL runs, but the raw data clearly have offsets
   (run03 sits around +0.6 V when I plot it).
2) The SNR values are about half of what my lab notebook gives.
   For run01 my notebook says about 9.2 dB; the program says 4.6 dB.
Nothing crashes, so I don't know where to look.
Start from the tip of day1-work (your feature is in). If you skipped the feature, git switch -c debug-work from main is fine.
1.5.1Reproduce with a failing test firstHUMANCHAT5 min
  • Write a test that fails because of the bug before touching the code. For symptom 1: load data/run03.csv, compute the raw mean of the signal, call analyze_run, compare the reported offset with the mean of a copy of the raw data taken before the call.
  • A failing test is the best bug report for an assistant too.
Check before you move on
  • The test fails. The failure message shows an offset near 0 instead of near 0.6.
Hint 1

from pulselab.io import load_run; from pulselab.report import analyze_run. Copy the signal with run['signal'].copy() before calling analyze_run.

Hint 2

Also check: is run['signal'] the same after analyze_run?

1.5.2Ask for ranked hypotheses, not a fixCHATPLAN6 min
  • Give the assistant the evidence: the symptom, expected vs actual, the failing test output, and the two relevant files. Ask for ranked hypotheses, each with one experiment that would confirm or reject it. Say explicitly: do not propose a fix yet.
Your prompt: write it yourself, fill the blanks
GOAL:         [find the root cause of ...; do not propose a fix yet]
CONTEXT:      [symptom, expected vs actual, files: pulselab/report.py, pulselab/preprocess.py, the failing test output]
CONSTRAINTS:  [no code changes; rank hypotheses by likelihood]
FORMAT:       [table: hypothesis | why plausible | experiment to confirm or reject]
VERIFICATION: [tell me what evidence would change your ranking]
Check before you move on
  • Each hypothesis comes with an experiment you can run in under a minute.
1.5.3Run the experiments yourselfHUMAN5 min
  • Run the discriminating experiment(s). For example:
python
from pulselab.io import load_run
from pulselab.preprocess import estimate_noise
run = load_run("data/run03.csv")
before = run["signal"].mean()
estimate_noise(run["signal"])
print(before, run["signal"].mean())        # what do you see?
  • Reject or confirm each hypothesis in your journal.
Check before you move on
  • You can state the root cause in one sentence with the file and the line.
1.5.4Fix at the root, minimallyEDIT8 min
  • Ask for the smallest fix at the cause. Then check what you got: did the assistant fix remove_offset/estimate_noise, or only patch analyze_run to work around it?
  • After the fix: your failing test passes and the other results (pulse counts, tau) are unchanged compared with baseline_summary.csv (only offset_V and snr_db may change).
  • Ask: "Where else in this project could the same hazard occur?" and verify the answer with a search.
Check before you move on
  • remove_offset no longer modifies its input, OR the caller passes a copy (justify your choice).
  • n_pulses and tau_s are identical to the baseline for all 6 runs.
Hint 1

A fix only in analyze_run leaves estimate_noise (and any future caller) able to corrupt its input: prefer fixing the function that mutates.

Hint 2

Compare only the columns you expect to change: load both CSV files with pandas and compare column by column.

1.5.5Second symptom: the SNR is off by a factor 2CHATHUMAN6 min
  • The notebook gives 9.2 dB for run01; the program printed 4.6 dB. Find why. Ask the assistant, then decide with your own domain knowledge: is the SNR here a ratio of amplitudes (RMS values) or of powers? Which formula in dB?
  • Fix, add a regression test with a case you can compute by hand (for example RMS ratio 10 → 20 dB), and check run01 now gives about 9.2 dB.
Check before you move on
